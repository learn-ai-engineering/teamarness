# 02-system/05-packages — Package Requirements

Prefix: `TEAM.SYS.PKG`

The Package system defines Package Manifests, Sources, Registrations, Admission, the Package Host, Package Process Protocol, Semantic Capabilities, lifecycle, SDKs, local data ownership, and trust. All product-domain behavior lives in Packages. Phase 3 delivered this foundation after the desktop Shell and Workspace onboarding path worked end to end.

## TEAM.SYS.PKG-R01 — Package Manifest

Every Package SHALL provide a Package Manifest declaring its stable Package Identity, compatibility requirements, Package Backend and Package UI entrypoints, and consumed versioned Semantic Capabilities. A Package Manifest SHALL NOT determine its Package Source, Package Registration Scope, Package Admission, or Package Trust. Teamarness SHALL validate the Package Manifest before Package Admission and SHALL reject invalid or unsupported declarations with an observable error.

## TEAM.SYS.PKG-R02 — Standard Lifecycle

The Package Host SHALL manage Package Instances through explicit `activate`, `suspend`, `recover`, and `dispose` lifecycle operations. A Package SHALL release lifecycle-scoped work during suspension and all owned resources during disposal. Hiding a Package UI or selecting another Workspace SHALL NOT itself suspend a Package Backend in Phase 3. When a Package Backend returns an error from activation, suspension, or recovery, the Package Host SHALL leave the Package Instance in `Failed` and SHALL NOT consume an automatic Package Process restart attempt. A returned disposal error SHALL NOT leave the Package Instance in `Failed`; disposal SHALL still leave the Package Instance in terminal `Disposed`. Unexpected Package Process exits, uncancellable execution deadlines, and missed health probes SHALL remain eligible for up to three automatic restart attempts after the initial failure. For trusted Packages, returned lifecycle errors, lifecycle task failures, Package Process exits, uncancellable execution deadlines, missed health probes, failed mounts, and JavaScript exceptions SHALL enter a recoverable or disposable state rather than terminate the Shell or Core Runtime. The Package foundation does not promise safe execution of hostile code, an operating-system sandbox, or recovery from system-wide resource exhaustion.

## TEAM.SYS.PKG-R03 — Semantic Capability Contracts

A Package SHALL access Teamarness-owned authority and generic behavior only through declared, versioned Semantic Capabilities. Capability calls and events SHALL be typed and SHALL NOT expose private keys, raw secret bytes, Core Runtime database handles, Core Runtime types, or raw transport handles. Activation SHALL fail clearly when Teamarness cannot fulfill a required capability version. Phase 3 SHALL provide capabilities for canonical Workspace metadata and membership, membership transitions, historical membership checks, and domain-separated signing. A Semantic Capability SHALL be identified by a family and a version; the Package Host and the Package SHALL negotiate one version within a family, and a new family SHALL be addable without changing the lifecycle contract, the Package Process Protocol, or the Package UI contract.

The `teamarness.principals` 1.0 capability SHALL provide Workspace-scoped current Workspace Principals, each with Principal ID, kind (`person` or `agent`), Steward, current keys, name, and fingerprint; lookup by member key or by Principal ID; and a resumable bounded snapshot invalidation stream. Its durable profile cursor SHALL be independent of membership epoch and record-log cursor. Missing profiles SHALL NOT be treated as failed membership authority; an unrelated Package may declare the same family without any Package-specific Host route. A Package SHALL attribute a record by resolving its signed author key through this family, never through a claim in a payload or request. The existing `teamarness.membership` 1.0 contract remains unchanged and remains the authorization view (ADR 0023).

The `teamarness.agent-binding` 1.0 capability SHALL let a Package Instance read its own Agent Binding (`current`), list the Workspace Agents this Installation stewards with their bound state (`candidates`), set it (`bind`) and clear it (`unbind`). The grant SHALL fix the calling Package and Workspace, so a Package SHALL NOT read or change another Package's binding. `bind` SHALL require this Installation to steward the Agent and SHALL otherwise refuse with `agent_not_stewarded`; an unknown Agent SHALL be refused with `agent_not_found`. A binding SHALL be Installation-local, SHALL NOT be replicated, SHALL be cleared when this Installation removes the Agent, and SHALL read as absent once the Agent is no longer current (ADR 0030).

## TEAM.SYS.PKG-R04 — Backend and UI Boundary

A Package Backend SHALL run as a self-contained executable in one host-supervised Package Process for each Package Instance. The versioned, typed Package Process Protocol SHALL be language-neutral and SHALL define handshake, lifecycle, requests, responses, events, cancellation, and shutdown without a Rust ABI or Rust type contract. Both peers SHALL classify every frame with one shared rule that yields three verdicts: deliver it, ignore it, or fail the process generation. A frame that the contract permits but whose request or stream the receiver has retired SHALL be ignored, and each side SHALL keep bounded tombstones entered when it stops being willing to serve that request or stream. Malformed traffic, a second terminal frame, a budget the contract fixes, and a frame naming state that never existed SHALL remain fatal. Internal queues, buffers and pages that carry protocol traffic SHALL be declared over the protocol constants they serve, and exhausting one SHALL be reported as backpressure or a retryable `overloaded` error rather than as a process exit or a permanent capability failure. Phase 3 SHALL ship a Rust Backend SDK and Rust reference Package. A Package UI SHALL be TypeScript web content mounted by the Shell in a sandboxed frame. Each Package UI SHALL own its header, secondary navigation, layout, and domain presentation inside its Shadow Root; shared Shell presentation support SHALL NOT take ownership of those structures. Package UI and Backend traffic SHALL use Package-owned typed contracts routed through the Shell's mount-scoped frame bridge and the generic Tauri invoke and event bridge.

## TEAM.SYS.PKG-R05 — Storage Ownership and Isolation

The Package Host SHALL assign each Package Instance a durable Package Data Directory keyed by Installation, Workspace, and Package Identity. The Package SHALL own its schemas, migrations, indexes, and stored data and MAY choose SQLite, files, or another local representation. The directory SHALL survive Package Source and version changes for the same Package Identity. No supported Teamarness contract SHALL expose Core Runtime storage or another Package's directory. This contract is not an operating-system filesystem boundary.

## TEAM.SYS.PKG-R06 — Common SDK

Packages from application, installation, and future Workspace registrations SHALL use the same Package Manifest, Package Process Protocol, lifecycle, Semantic Capabilities, UI contracts, data-directory contract, bridge, and theme contract. Phase 3 SHALL ship a Rust Backend SDK and TypeScript UI SDK but SHALL NOT require the Package Process Protocol to be implemented in Rust. The TypeScript UI SDK SHALL publish the exact frozen semantic token-name authority and MAY provide an optional framework-neutral, class-scoped CSS kit with overlapping-safe idempotent installation cleanup. Using the kit SHALL remain optional and SHALL NOT change Package ownership of its UI composition. Package Registration Scope and Package Trust policy MAY restrict discovery or execution but SHALL NOT create separate programming models. A Package-owned error's stable code, retryability and bounded details SHALL reach the Package UI unchanged beside the Teamarness error code. Teamarness SHALL provide an author-runnable validator that applies the same Package Manifest and UI contract rules as Package Admission.

## TEAM.SYS.PKG-R07 — Trust Boundary

Teamarness SHALL grant Package Trust during Package Admission. A Package Manifest SHALL NOT grant trust to its own Package. Phase 3 SHALL admit application-bundled Package Sources and explicitly registered installation-local Package Sources as trusted. The Package Process boundary SHALL protect the Shell and Core Runtime from ordinary Package exits and missed execution deadlines, but Phase 3 SHALL NOT claim that it safely contains hostile or unreviewed code or restricts ambient filesystem and network authority.

## TEAM.SYS.PKG-R08 — Reference Package

Phase 3 SHALL include one trusted reference Package loaded from both an application-bundled Package Source and an explicitly registered installation-local Package Source. Both SHALL use the same Package-owned code and contracts. The reference Package SHALL exercise Package Manifest validation, Package Admission, capability negotiation, lifecycle transitions, its Package Data Directory, typed calls and events, inherited Workspace theming, and supported failure recovery end to end without introducing product-domain behavior.

## TEAM.SYS.PKG-R09 — Source and Registration

Phase 3 SHALL discover Package Sources through application and installation Package Registrations. An installation-local registration SHALL identify a Package Directory containing one Package Manifest and its Package Artifacts. An installation registration MAY replace an application registration for the same Package Identity only when it carries the expected identity and explicit local trust evidence. No Package Source SHALL win implicitly. Package Admission SHALL have two tiers (ADR 0036). The Team tier SHALL hold the application registrations and every installation registration that overrides one; it SHALL be admitted at Host open and SHALL NOT change while the Host runs, so writing or removing an override SHALL take effect at the next Host open. The Personal tier SHALL hold every other installation registration. Installing, reloading, or removing a Personal registration SHALL take effect while the Host runs, without an application restart, without restarting any Team Package Instance, and without deleting the Package Data Directory. A registration written or edited outside Teamarness SHALL take effect at the next Host open. Teamarness SHALL let the Shell write the installation registration file only after an admission preflight that records nothing, under the same file policy as a hand-written file; it SHALL keep every other entry, write atomically, and SHALL NOT rewrite a file that breaks that policy. Installing SHALL require explicit acceptance of the native-code risks, and an override SHALL require a second, separate confirmation. Invalid paths, missing or incompatible Package Artifacts, malformed Package Manifests, unsupported versions, and unresolved duplicate Package Identities SHALL fail with stable observable errors without preventing other Packages or Teamarness from remaining usable. Teamarness SHALL NOT fetch remote Packages, resolve Package dependencies, or perform Package Git operations in Phase 3.

## TEAM.SYS.PKG-R10 — Synchronization Capability Boundary

A Synchronization Capability SHALL provide generic, versioned, Package-scoped replication through Core Runtime-owned transport. The first capability is `teamarness.synchronization.immutable-record-log` 1.x with `append`, `subscribe`, and `open`. It uses implicit grant scope, bounded canonical and sealed values, committed content-idempotent append, and an at-least-once local cursor stream. Minor 1.1 SHALL accept an optional `principal` on `append`: Core SHALL sign with that Workspace Agent's key for any Package Instance on this Installation when the Agent is current, this Installation stewards it, and at least one Package Instance on this Installation holds an Agent Binding to it, and SHALL otherwise refuse with `principal_not_bound` (ADR 0023, ADR 0030). A Package SHALL retain ownership of its domain records, schemas, projections, and policy. Packages SHALL NOT receive Iroh, P2Panda, SQLite, private-key, or raw-key types. Future family members may support mutable structured state, collaborative documents, or custom transport without changing Package lifecycle, Package Process, or Package UI mounting contracts. The capability SHALL report availability (`waiting_for_history_access`, `offline`, `catching_up`, or `current`) with a pending record count, and stable warning codes, as defined by the capability contract. A record-log stream SHALL report changed availability without requiring a new record; page and availability reads SHALL NOT consume its independent notification before the stream can report the change. An explicit peer-busy response SHALL preserve the prior reachability observation while retaining bounded retry/backoff; it SHALL NOT assert either failure or reachability. A subscription cursor that does not match the local journal SHALL be reported so the Package can reset it.

## TEAM.SYS.PKG-R11 — Native Trust Limits

A trusted Package Process MAY use ordinary native filesystem and network access under the current user's authority. Teamarness SHALL identify installation-local Packages and SHALL NOT describe process separation as a sandbox. Teamarness-owned identity, canonical membership, signing, and Iroh transport SHALL remain available only through Semantic Capabilities. Because trusted Package Processes run with the user's authority, they can read the Core Runtime's private data directory, including the Installation secret, Content Keys, and Package Registrations. The Semantic Capability boundary is a supported-contract boundary, not a confidentiality boundary against trusted Package code.

## TEAM.SYS.PKG-R12 — Port Contract Declarations and Authoring Catalog

A Package Manifest MAY reference one bounded, digest-verified provided Port Contract document and SHALL declare individually named and kinded consumed Ports by independent contract identity and compatible major/minor range, required by default. Port Contracts SHALL name and describe each command, query, or event and provide request/response or event JSON Schemas as appropriate. A streaming query SHALL be a query with request and event schemas. The document and manifest declarations SHALL reject unknown fields, duplicate identities and ports, non-normalized paths, oversized files, invalid version ranges and invalid schemas. Port names SHALL follow the dotted operation grammar; English naming advice SHALL be a warning, not an admission failure. Minor versions SHALL retain every existing Port and its kind and schemas, permitting new Ports and description edits; a compatibility comparison requires both versions as input. The author validator and Host SHALL share local declaration validation. A read-only authoring catalog SHALL expose locally valid installed Packages' complete declared provided and consumed relationships, descriptions, schemas and graph-admission diagnostics, including declarations rejected by graph admission, without pushing all schemas into each UI snapshot. Installation-wide dependency diagnostics and runtime availability are governed separately by R13.

## TEAM.SYS.PKG-R13 — Port Admission and Scoped Routing

Admission SHALL resolve at most one valid Provider for each Port Contract per Installation, retain a valid incumbent, and reject conflicting Providers without affecting unrelated Packages. Required missing or incompatible consumed Ports SHALL refuse the Consumer with stable diagnostics; absent optional Ports SHALL remain discoverably unavailable. The Host SHALL broker exact granted Ports only within the caller's Workspace, using the calling Instance's current Principal binding for actor context rather than a payload claim. A Consumer SHALL explicitly request a command, query, or subscription; declarations SHALL neither subscribe nor awaken Consumers. Existing Packages SHALL remain eager by default; an opt-in on-demand Provider SHALL start on first use, UI mount or explicit activation. Provider selection SHALL run per admission tier (`TEAM.SYS.PKG-R09`): a Team Package SHALL NOT route to a Personal Provider, and a Team Consumer of a contract that only a Personal Package provides SHALL see it as unavailable. A Personal Package that claims a Port Contract a Team Package provides SHALL be refused with `port_provider_conflict`. A live Personal install or reload whose candidate claims a Port Contract that another running Package already provides SHALL be refused with `port_provider_conflict`. A live Personal change SHALL re-resolve and restart only the Personal Consumers whose selected route changed; Team routes SHALL NOT change while the Host runs. A Consumer SHALL explicitly declare `teamarness.package-ports` 2.0 and select `access` and the contract `major` on invocations and subscriptions. Declared access SHALL use actual manifest dependencies; optional absence SHALL be reported as `port_unavailable`, not an implicit route. Calls SHALL reject undeclared Port names/kinds and caller-supplied target Workspace, Provider or actor. A current Instance SHALL present its Host-derived actor: the Workspace Agent the calling Instance is bound to through `teamarness.agent-binding`, otherwise its Installation Person. An actor SHALL NOT be inferred from a caller claim (ADR 0030). Before initializing or activating a replacement Backend generation, the Host SHALL fence the prior generation's Agent actor lookup and Agent binding writes: already-running Core critical sections SHALL finish before replacement, and queued old-generation actor lookups and bind/unbind writes SHALL be refused after advancement. Cancellation or timeout of an asynchronous waiter SHALL NOT release ownership of such still-running Core work. This ordering SHALL survive same-Host Instance reconstruction; it does not promise retraction of all detached capability or Provider effects. Package Process Protocol SHALL remain 1.0. Only package-ports 2.0 SHALL be offered in this pre-release transition; major-1 declarations SHALL fail negotiation without a legacy dispatcher (ADR 0035).


Declared metadata SHALL be available without an Agent Binding through bounded `available` pages and `describe` chunks compiled from the current Port snapshot, which each operation SHALL read once (ADR 0036). Pages SHALL contain at most 32 summaries and 32 KiB encoded JSON; chunks SHALL contain at most 64 KiB decoded bytes in padded base64. The complete deterministic compact UTF-8 document SHALL retain descriptions, exact declared Ports, their distinct request/response/event schemas, and all reachable local definitions, up to the admitted 1 MiB bound. SHA-256 SHALL identify the exact projected bytes. Discovery SHALL NOT start a Provider or expose graph-rejected candidates. Cursors SHALL bind caller, Workspace, access, admission revision, and last sorted identity; malformed, cross-scope, or stale cursors SHALL be refused with `port_catalog_changed`, including after Host replacement or after a Personal tier change. Inaccessible or unavailable metadata and invalid offsets SHALL be refused, not truncated.

A conforming `runtime.guide` SHALL mark a contract as agent-facing: an ordinary query with a closed empty-object request and a closed response requiring a bounded `markdown` string, resolving local references. Malformed guide shapes SHALL produce author warnings and remain ordinary declared composition. Bound-Agent access to a guide-bearing contract SHALL default to `port_not_enabled`, even for declared Ports. Agent-only access SHALL require a current binding and SHALL NOT fall back to Person authority. A declared no-guide contract SHALL remain ordinary composition.

Agent discovery SHALL require a current binding and SHALL expose eligible admitted guide-bearing contracts and retained unavailable selections without starting Providers. A Team caller SHALL consider Team Providers only; a Personal caller SHALL consider Team and Personal Providers. A Provider whose required Port is unavailable SHALL NOT be offered. Agent metadata SHALL contain all Ports and reachable definitions. `major`, `minor`, description and digest SHALL identify the current offered contract when eligible; `enabled` and `enabledMajor` SHALL identify the saved selection independently. An incompatible saved major SHALL make the selection unavailable without hiding current offered metadata or changing settings. A missing or nonconforming Provider SHALL leave only an unavailable retained row without current metadata.

The Host SHALL persist selected majors in its existing private store under Installation, Workspace, calling harness Package Identity and contract. Selections SHALL default to empty and survive restart, rebind, unbind and reinstall under the same identities. Enable and disable SHALL require a current binding and generation, be idempotent and accept no scope or actor selectors. Enable SHALL require a conforming admitted Provider of the requested major; disable SHALL work while its Provider is missing. Both access views SHALL use one resolved route and the existing broker dispatch. Dynamic access SHALL require no consumed-Port declaration, and a saved major SHALL NOT replace a real declared dependency.

A per-harness operation gate SHALL serialize settings, binding changes and authorization. Actual blocking store work SHALL own both the gate and generation lease after waiter cancellation. The Host SHALL report success only after durable completion and SHALL reread durable settings before further authorization after uncertain completion. It SHALL NOT hold the operation gate through Provider command execution.

Subscription leases SHALL identify Workspace, harness, contract, access basis, binding and process authority generation. Disable SHALL revoke Agent-authorized subscriptions through either access view with `port_not_enabled`; unbind or accepted Agent removal SHALL use `agent_not_bound`, and binding a different Agent SHALL use `agent_binding_changed`. Same-Agent idempotent bind MAY retain streams; unbind followed by rebind SHALL NOT. Local binding transitions SHALL notify directly after durable success, under the operation gate. Existing Core principals notifications SHALL reconcile idle subscriptions after accepted local or remote membership loss. Revocation and enqueue SHALL share one delivery gate: accepted bounded queues MAY drain, but no new event SHALL enqueue after revocation. A Consumer withholding credit SHALL NOT prevent revocation or permit release. Unrelated subscribers SHALL retain their shared upstream and order; its last subscriber leaving SHALL close it.

Provider suspend, exit, disposal or generation replacement SHALL end affected live queries and events with `provider_exited`. Recover SHALL permit explicit reconnect without reviving old subscriptions or replaying commands. Settings SHALL remain unchanged. Already-authorized commands SHALL retain their actor and existing certainty verdict; subsequent authorization SHALL use current authority. Harness generation cleanup SHALL affect only that generation.

**Qualification:** Host integration tests cover both access views, real durable settings and lifecycle revocation. `tests/system/tests/agent_port_discovery.rs` drives a source-built generic client with no consumed-Port declarations through complete metadata, Conversations guidance, Agent-attributed posts, reconnect recovery, disable, rebind, unbind and restart. Shared broker tests exercise validation, non-object values, isolation, actors, generation retirement, overload, event bounds and command uncertainty through both views. Scripted repository evidence and local desktop bundles do not qualify the external Agent UI or model endpoint. Those observations and fresh external build provenance remain required before claiming the full user journey.

## TEAM.SYS.PKG-R14 — Port Payloads and Live Delivery

The Host SHALL validate request payloads before forwarding and response, query-stream and event payloads before delivery. Schema failures SHALL affect only that call or stream. Events SHALL be live-only and at-most-once with no replay or inactive Consumer wakeup. An event subscription SHALL have finite credit and independently bounded buffers; an overflowing subscriber SHALL fail observably after its accepted queued events without delaying peers, which SHALL receive one Provider's emitted events in order. One upstream Provider stream SHALL serve active subscribers for each Workspace/event Port and close after its last subscriber; global and per-Provider subscriber, stream and byte permits SHALL be derived from the published process frame, writer and credit bounds. SDK inbound event lag SHALL retire only the affected stream, not the Package session. A Provider exit or stall SHALL leave other processes operational. A command that may have reached its Provider SHALL report an unknown outcome with `outcomeUncertain:true` and `retryable:false` (the terminal code MAY identify an invalid response or Provider-owned error) and SHALL NOT be automatically retried; a pre-writer-acceptance rejection SHALL remain certain. Broker route and byte permits SHALL be bounded across the Host and lower per Provider generation than the process request/stream ceilings, reserving UI and lifecycle traffic. Queries promise read-only behavior by Provider contract; the Host does not prove purity. The Host SHALL not delegate Agent signing keys across Packages. For a Host-derived Person actor, the Conversations Provider SHALL refuse a post unless that Person matches its local Installation. Agent actors SHALL follow the existing Agent-authority rule in `TEAM.SYS.CONV-R18` (ADR 0030), using the Host-derived binding specified in R13. Its `message.page` query SHALL not mark a Channel read, and its `messages.changed` event SHALL be a coalescible projection invalidation without an initial event or replay. Consumers SHALL re-query after reconnecting. A Consumer that processes newly delivered Conversations Messages SHALL use the revision-based `message.changes` query (Port Contract 1.2, `TEAM.SYS.CONV-R19`) or an equivalent complete reconciliation, not infer delivery progress from Message display positions or timestamps. An invalidation SHALL NOT be treated as one Message or a replay cursor.

## TEAM.SYS.PKG-R15 — Local Port Observations

The Host MAY expose an opt-in, bounded, read-only Port observation receiver that relates each Consumer process-scoped `p:` ID to a Provider `h:` ID after dispatch. A pre-dispatch refusal SHALL have no Provider ID. A shared event upstream SHALL relate one Provider stream to each Consumer process scope and stream. The SDK MAY expose an opt-in, bounded Provider observation receiver with the existing `h:` ID. Neither receiver SHALL block a Port, forward payloads or actor identity, or change the command's uncertainty verdict. Lag and process death MAY leave an incomplete trace. Observations SHALL not prove a domain outcome or constitute a Shell diagnostics interface.

## TEAM.SYS.PKG-R16 — Content Views

The `teamarness.content-views` 1.0 capability SHALL let a Package open a read-only view over 1 to 1,000 files in its own Package Data Directory and close it. `open` SHALL take an entry path and, for each file, a content path, a lowercase SHA-256, a size and a `{kind:"file", path}` source, and SHALL return an opaque 128-bit view token and the URL `teamarness-content://localhost/<token>/<entry>`. The grant SHALL fix the Package, Workspace and process generation, so a request SHALL NOT name a Package or a directory. The Host SHALL refuse an extension outside the shared media-type allowlist with `unsupported_media_type`; more than 1,000 files, a declared total over 64 MiB or a file over 16 MiB with `content_too_large`; and a malformed or duplicate path, an unlisted entry, or a missing, symlinked, non-regular or escaping source with `invalid_content_path`. The Host SHALL assign every media type from the allowlist, never from the Package. It SHALL serve only listed files, SHALL check size and SHA-256 on the first read of each file in a view, and SHALL answer an unknown or ended view, an unlisted path and a file that fails verification with the same `content_not_found`. A file that changes after `open` SHALL NOT be served; showing it SHALL need a new view. A process generation SHALL hold at most 32 open views, and every view SHALL close when its generation ends. The allowlist, bounds and path rules SHALL be published once in `teamarness_package_contract::media_types` so that a Package can refuse a file with the Host's verdict (ADR 0034).

Traces to: `TEAM-R07`.

## TEAM.SYS.PKG-R17 — Nested Content Frames

The Shell SHALL serve Content Views through the `teamarness-content:` scheme with the same request rules as the Package resource scheme, and every response, including every refusal, SHALL carry the Shell-owned content policy: the CSP directive `sandbox allow-scripts`, which gives content an opaque origin, `connect-src teamarness-content:`, `frame-src 'none'`, no workers, plugins or forms, `nosniff` and `no-store`. Content SHALL stay opaque-origin even when the embedding frame omits a `sandbox` attribute. Declaring `teamarness.content-views` SHALL be the only opt-in to nested content: the Host SHALL report `nestedContent: true` on that Package's UI mounts, and only those mounts SHALL receive `frame-src teamarness-content:` in place of `frame-src 'none'`, with no other policy change. Every other mount SHALL keep `frame-src 'none'`. The handler SHALL answer one satisfiable byte range with `206` and an unsatisfiable range with `416`, so media can seek. The packaged-app smoke SHALL keep a database-backed probe proving that content frames reach no Tauri command, because content frames can reach `webkit.messageHandlers.ipc` as Package UI Frames can (ADR 0015, ADR 0034).

**Verification gap:** Network denial from content frames is incomplete and untested: navigation and WebRTC are not controlled. See [DELTA-015](../../.delta/DELTA-015-exhibit-content-network-access.md); this note does not weaken R17. The packaged-app smoke's frame without a `sandbox` attribute is nested in a sandboxed Package UI Frame and inherits its `sandbox` flags, so the smoke proves the end-to-end opaque origin, and the `content_protocol.rs` tests prove the CSP `sandbox` directive at header level.

Traces to: `TEAM-R07`, `TEAM-R08`.

## TEAM.SYS.PKG-R18 — Exhibits Port Contract

The bundled Exhibits Package (`dev.teamarness.exhibits`) SHALL own Exhibit Drafts in its Package Data Directory, SHALL NOT replicate them, and SHALL provide the `dev.teamarness.exhibits` 1.0 Port Contract with `runtime.guide`, `file.put`, `files.missing`, `draft.update`, `exhibit.list`, `exhibit.read`, `file.read` and `draft.delete`. It SHALL accept the Host-derived Person actor and a bound Workspace Agent actor (ADR 0030) and SHALL start on demand. Files SHALL arrive as idempotent, content-addressed 131,072-byte chunks in any order and SHALL be verified against their declared size and SHA-256 before a Draft can name them. `draft.update` SHALL replace a Draft's title, entry page and complete file list atomically, SHALL refuse a stale `expectedRevision` with `exhibits.revision_conflict`, and SHALL name at most 32 missing files with a `missingCount`; `files.missing` SHALL be read-only and SHALL report the chunks a Consumer must send to resume after an uncertain `file.put`. `exhibit.list` SHALL return Exhibits newest first, at most 64 per page, and `exhibit.read` SHALL page files 500 at a time. Every request and response SHALL stay under the 256 KiB Port payload bound at the published limits. `runtime.guide` SHALL publish the limits the Backend enforces, the media-type allowlist and the Exhibit ID pattern, and every Port SHALL carry a `description`. A refusal SHALL use a stable `exhibits.*` code, which a Consumer receives as `provider_error` with `details.provider.code`. The Exhibits UI SHALL list Exhibits newest first, show a selected Draft in a nested `sandbox="allow-scripts"` frame through a Content View, show a newer revision without reselection, and trust no message from that frame.

Snapshots and sharing are Exhibits slice 2 and are not required by R18.

Traces to: `TEAM-R06`.

## TEAM.SYS.PKG-R19 — Package Presentation, Package Page, and Settings View

A Package Manifest MAY declare an optional description, author, and homepage in `presentation`. Each SHALL be bounded, and the homepage SHALL be an absolute `https://` URL. An invalid value SHALL fail validation with `manifest_malformed` and a pointer to the field. A manifest without these fields SHALL remain valid. The Package Catalog SHALL carry the declared fields and omit absent ones.

The Shell SHALL give every admitted Package and every refused installation registration a Package page. The page SHALL show the Package's name, Package Identity, version, the optional metadata it declares, its admission tier (Team or Personal), Package Trust, declared Semantic Capabilities, and provided and consumed Ports, with the availability of each consumed Port. The page of a Personal Package SHALL also offer Reload, Restart, pause and resume or start, and Remove. The page of a Team Package SHALL NOT offer them. Remove SHALL state that the Package's data stays on this device.

A Package Manifest MAY declare UI views beside its implicit main view in `ui.views`. In manifest version 1 the only declarable view SHALL be `settings`, at most once; any other value or a repeat SHALL fail validation with `manifest_malformed`. A UI mount SHALL open the main view unless it names another view. A view the manifest does not declare SHALL be refused with `ui_view_not_declared` and SHALL leave any existing mount unchanged. The mount context SHALL carry the view. When a Package declares the settings view and has a Package Instance in the current Workspace, its Package page SHALL link to that view, and the Shell SHALL name the view and offer a way back to the main view.
