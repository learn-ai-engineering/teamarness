# Package source contracts v1

This directory defines the JSON documents consumed during Package Admission.

- `teamarness.package.json` is UTF-8 JSON limited to 256 KiB. It declares Package-owned identity, compatibility, artifacts, and UI contracts. It cannot declare source, trust, registration scope, override policy, or data paths.
- `application-packages.v1.json` is a build-generated list of normalized Package Directory paths relative to the application resource root.
- `<app-data>/packages/registrations.v1.json` is an owner-only installation file. Local directories are absolute. Trust requires the exact `trusted_native_code_v1` risk set. `overrideApplication` must be true to replace an application registration. The Host's registration store can write this file: it refuses to rewrite a file that breaks this policy or does not parse, keeps every other entry, and writes atomically (a `0600` temporary file in the `0700` `packages/` directory, synced and renamed). It writes an entry only after a preflight admission, which records nothing in the Host store or UI cache, admits the candidate.

Admission has two tiers (ADR 0031). The **Team tier** is the application registrations plus installation registrations with `overrideApplication: true`; it is admitted first and selects Port providers among Team Packages only. The **Personal tier** is every other installation registration; it is admitted next against the fixed Team graph. A Personal Package may consume Team and Personal providers. A Team Package never routes to a Personal provider: a Team consumer of a contract that only a Personal Package provides sees it as unavailable. A Personal Package that provides a contract a Team Package provides is refused with `port_provider_conflict`. The Host snapshot lists every installation registration with its tier and its status, `admitted` or `refused` with a code.

A UI contract is a closed version 1 document with `$defs`, `requests`, and `subscriptions`. A request operation declares separate `request` and `response` schemas. A subscription operation declares separate `request` and `event` schemas. Operation names are 1 to 128 ASCII bytes and match `^[a-z][a-z0-9_-]*(\.[a-z][a-z0-9_-]*)*$`.

Admission permits at most 128 request operations, 128 subscription operations, and 256 operations in total. It accepts only `#/$defs/...` references and rejects dynamic references, missing definitions, cycles, schema depth above 64, more than 16,384 schema nodes, and contract files above 1 MiB. The host compiles all four validator directions during admission. Generic request, response, subscription, and event payloads are limited to 256 KiB of encoded JSON and a depth of 64.

The UI entrypoint must be UTF-8 ESM and no larger than 8 MiB. A Package may declare at most 64 UI assets, each no larger than 8 MiB. The entrypoint, assets, and contract may total at most 32 MiB. The host copies admitted resources to its private cache and resolves them only through an opaque mount token. Source paths, cache paths, and admission digests are not public catalog values.

`presentation` requires `displayName` and may declare three optional fields that the Host shows in its catalog:

- `description` is 1 to 1024 characters with no leading or trailing whitespace. It may contain line feeds (`\n`) but no other control characters.
- `author` is 1 to 128 characters with no control characters.
- `homepage` is an absolute `https://` URL with a host and no user information, whitespace, or control characters, at most 2048 characters.

Lengths count Unicode code points, as JSON Schema `maxLength` does. A field that breaks its rule fails with `manifest_malformed` and a pointer such as `/presentation/homepage`. A manifest without these fields remains valid.

Unknown fields fail each host-owned document. A manifest may carry Package-owned values only inside `extensions`, whose keys are reverse-DNS namespaces. JSON objects reject duplicate keys before schema decoding.

A manifest may additionally declare `portContract: {"path":"ports.json","sha256":"..."}` and `consumedPorts: [{"identity":"dev.example.conversations","major":1,"minMinor":0,"maxMinor":1,"required":true,"ports":[{"name":"conversation.list","kind":"query"}]}]`. `required` defaults to true. Every consumed entry names an exact nonempty set of ports and kinds, not an entire contract. The path uses the same normalized relative-path and no-symlink rule as the UI contract, and its file is digest-verified and limited to 1 MiB. See `contracts/package-ports/v1/README.md` for the separate provided contract profile. The optional `activation` field is `"eager"` or `"on_demand"`; absence defaults to eager startup. On-demand Instances are prepared at Host open and Workspace reconciliation, then start on an explicit activation or UI mount (and on first port use once broker routes are available). A running Instance stays active when its UI closes. A running Host installs, reloads, and removes a Personal Package live, one at a time, without restarting any Team Package; a live candidate that claims a contract a running Package already provides is refused with `port_provider_conflict`. Team-tier changes (overrides) and hand-edited registration files are admitted on the next Host open. Older manifests without these fields remain valid. Local declaration validation does not claim to have checked installation-wide provider availability or previous versions that were not supplied. The standard assembler copies a provided Port document to the declared path and computes `portContract.sha256` after building the Backend and UI. For example, `packages/conversations-package/ports.json` is staged beside its UI contract; changing its bytes requires a new manifest digest.
